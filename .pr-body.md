## What

Repository scaffold for the Context Engineering Runtime, landed before any core code.

- `pyproject.toml` with ruff, mypy **strict**, pytest + coverage, bandit, and an
  explicit optional-dependency split (embeddings / otel / ollama / dev).
- Cross-platform `Makefile`. No shell-isms, so `make demo` behaves identically on
  Windows and Linux rather than being green only in CI.
- GitHub Actions pipeline: build, test (offline, no API key), lint, format check,
  typecheck, bandit, pip-audit, dependency audit, a dedicated legibility gate, and a
  benchmark-reproducibility job.
- pre-commit hooks and `.gitattributes` pinning LF so the history is byte-stable.
- `DESIGN.md` written **before** the first line of core code, as required.
- `src/cer/errors.py`: typed exception hierarchy, every error carrying a remedy.
- `src/cer/types.py`: immutable `TokenBudget`, `Provenance`, `Utility`, `BlockRole`.
- `src/cer/config.py`: the single `ContextConfig` object. No global mutable state.
- Executable checks: `scripts/dependency_audit.py` (fails on any vendor SDK or agent
  framework in the core), `scripts/check_docs.py`, `scripts/verify_quickstart.py`,
  `scripts/clean.py`.
- Docs: README, ARCHITECTURE (Mermaid), DECISIONS (11 autonomous decisions recorded),
  CONTRIBUTING, CHANGELOG, ROADMAP, EXAMPLES, and 4 ADRs.
- Social preview image.

## Why

The brief requires a green `make build / test / lint / bench` from a clean checkout,
>=80% coverage, a dependency audit that proves the no-vendor-SDK claim, and a
DESIGN.md that predates the code. Encoding those as executable checks rather than
good intentions means a stubbed doc or a sneaking vendor import fails CI instead of
being discovered at release time.

Two decisions worth flagging in review:

1. **The Makefile avoids POSIX shell constructs.** The dev machine is Windows with GNU
   Make and no bash on PATH. Hard-coding `SHELL := bash` would make local `make demo`
   fail while CI stayed green, which is precisely the false-green this project argues
   against. See DECISIONS.md D-011.
2. **The dependency allowlist is explicit.** Adding a core dependency is a deliberate
   edit to `ALLOWED_CORE`, not an accident of running `pip install`.

## How to verify

```bash
make install
make lint        # ruff check + format check
make typecheck   # mypy strict, zero suppressions
make test        # 60 tests, 100% coverage on the core modules
make audit       # dependency audit passes: 2 core deps, no vendor SDK
make docs-check  # all 9 required docs + 4 ADRs present and non-trivial
```

Verified locally on Windows: ruff clean, mypy strict clean, 60 passed, 100% branch
coverage, docs check passing.
